Deployment runbook · one VM · Docker Compose + Caddy

Getting PlugSure onto a server an Autel unit can reach

Nine steps from a bare Ubuntu VM to a charge point holding a live WebSocket. Every step says what correct output looks like, so you can tell whether it worked before moving on.

Audience: comfortable with Linux Time: 2–3 hours, most of it DNS propagation Deeper reference: deploy/README.md in the repo
Three settings that are not optional

OCPP_MIN_SECURITY_PROFILE=2 — at the code default of 0 there is no per-charger authentication at all. Anyone who can reach the OCPP port can open a session as any charge point and write into your billing data. The API key you give Autel does not constrain that, because it is a different port and a different mechanism.

OCPP_TRUST_PROXY_PROTO=true — TLS terminates at Caddy, and without this the gateway cannot tell that it did. It would refuse every charger with 403. The gateway now refuses to start in that combination, so you will find out immediately rather than during the vendor visit.

Run as plugsure_app, never the database owner. A superuser bypasses every row-level security policy. The process refuses to start that way under NODE_ENV=production.

What you need before step 1

ThingDetailWhy it matters
VMUbuntu 24.04 LTS, 2 vCPU / 4 GB, 20 GB disk. AWS ap-southeast-3 (Jakarta) if you are on AWS.Postgres and both processes on one box is fine for one charger. The OCPP frame log is chatty — plan for disk growth.
Static IPElastic IP or equivalentThe charger's Central System URL is flashed into the hardware. If the address moves, that is a site visit per unit.
DomainA name you control, e.g. ocpp.plugsure.idLet's Encrypt needs a real hostname. A charger will not accept a self-signed certificate.
Ports open443 and 80 from anywhere; 22 from your office only443 for chargers, 80 for the ACME challenge, 22 for you. Not 9200 and not 5432.
Agree the hostname with Autel first

The Central System URL goes into every unit's firmware config. Changing it later means physically visiting each charger. Decide the hostname before anyone touches a charge point.

The nine steps

Run these in order. Each one depends on the previous one having worked.

01

Install what the VM needs

on the VM
$ sudo apt-get update
$ sudo apt-get install -y ca-certificates curl postgresql-client-16 \
    docker.io docker-compose-v2 debian-keyring debian-archive-keyring apt-transport-https

# Caddy, from its own repository
$ curl -1sLf https://dl.cloudsmith.io/public/caddy/stable/gpg.key \
    | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
$ curl -1sLf https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt \
    | sudo tee /etc/apt/sources.list.d/caddy-stable.list
$ sudo apt-get update && sudo apt-get install -y caddy
Check 
$ docker compose version   →  Docker Compose version v2.x
$ caddy version            →  v2.x
02

Point DNS at the VM, and prove it

One A record, TTL 300:

dns zone
ocpp.plugsure.id.     A     <YOUR_ELASTIC_IP>     300
verify before touching acme
$ dig +short ocpp.plugsure.id
$ curl -sI http://ocpp.plugsure.id/ | head -1
Expected

dig prints your Elastic IP and nothing else. If it prints an old address or nothing, wait — do not continue.

Let's Encrypt rate limits

Five failed validations per hostname per hour. Discovering a firewall problem against the production CA locks you out for an hour. Confirm DNS resolves and port 80 reaches the VM first.

03

Get the code onto the VM

on the VM
$ sudo mkdir -p /opt/plugsure && sudo chown $USER /opt/plugsure
# unzip the delivered archive, or clone your repo
$ cd /opt/plugsure && unzip ~/plugsure-v3.zip && cd plugsure
$ npm ci --dry-run
Expected 
added 38 packages, removed 1 package, and changed 7 packages

If this says ETARGET, stop — you have an older copy of the tree. The lockfile drift that caused it is fixed in this build.

04

Write the environment file

Generate the two secrets first. Keep them. Rotating AUDIT_HMAC_KEY later stops every previously written audit entry from verifying.

generate
$ openssl rand -hex 32   # → AUDIT_HMAC_KEY
$ openssl rand -hex 32   # → SECRETS_KEY
$ openssl rand -hex 24   # → POSTGRES_PASSWORD
$ openssl rand -hex 24   # → POSTGRES_APP_PASSWORD
/opt/plugsure/plugsure/.env
NODE_ENV=production
TZ=Asia/Jakarta

# Database. The apps connect as the SECOND one, not the first.
POSTGRES_PASSWORD=<owner>
POSTGRES_APP_PASSWORD=<runtime role>

# No defaults. Compose refuses to start without these.
AUDIT_HMAC_KEY=<32 bytes hex>
SECRETS_KEY=<32 bytes hex>

# The three non-negotiables from the top of this page.
OCPP_MIN_SECURITY_PROFILE=2
OCPP_TRUST_PROXY_PROTO=true
OCPP_AUTO_ADOPT=false

# Caddy is on the same host and is the only thing in front of us.
API_TRUSTED_PROXIES=127.0.0.1

# Bind both app ports to loopback. Caddy reaches them; the internet does not.
OCPP_BIND=127.0.0.1
API_BIND=127.0.0.1
lock it down
$ chmod 600 .env
Why two database passwords

Migrations issue DDL and run as the owner. The gateway and API run as plugsure_app, which cannot create tables and cannot bypass row-level security. The migration step provisions that role from POSTGRES_APP_PASSWORD — you do not create it by hand.

05

Configure Caddy and get the certificate

on the VM
$ sudo cp deploy/Caddyfile /etc/caddy/Caddyfile
$ sudo sed -i 's/ocpp\.example\.id/ocpp.plugsure.id/g; s/ops@example\.id/ops@plugsure.id/' \
    /etc/caddy/Caddyfile
$ sudo caddy validate --config /etc/caddy/Caddyfile
$ sudo systemctl reload caddy
$ sudo journalctl -u caddy -f
Watch for 
certificate obtained successfully

The shipped Caddyfile already does the two things that matter: it proxies /ocpp/* to 127.0.0.1:9220 without touching the Sec-WebSocket-Protocol header, and it assigns X-Forwarded-Proto rather than appending to whatever the client sent — so a charger cannot claim TLS it does not have.

Rehearse against the staging CA

Uncomment the acme_ca line in the Caddyfile's global block, reload, confirm issuance works end to end, then comment it out and delete the staging certificate or Caddy keeps serving it:

$ sudo rm -rf /var/lib/caddy/.local/share/caddy/certificates
$ sudo systemctl restart caddy
06

Bring the stack up

on the VM
$ docker compose build
$ docker compose up -d
$ docker compose ps
Expected 
migrate    Exited (0)
postgres   healthy
gateway    healthy
api        healthy

Boot order is enforced by the compose file, not by luck: postgres healthy → migrate exits 0 → gateway and api. The apps cannot start against an unmigrated database.

Now confirm the two things that silently go wrong.

the check that matters most
$ docker compose logs api | grep 'row-level security'
Must say 
row-level security is in force for application queries

Anything else means the apps are running as a superuser and tenant isolation has one line of defence instead of two.

and the gateway
$ docker compose logs gateway | grep -E 'listening|profile'
Must show 
"minSecurityProfile": 2, "tls": "expected at proxy"

If the gateway exited instead, read the error — it will tell you exactly which of TLS or OCPP_TRUST_PROXY_PROTO is missing. That refusal is deliberate: the alternative is a gateway that looks healthy and rejects 100% of chargers.

07

Seed, and capture your API key

on the VM
$ docker compose run --rm migrate node dist/db/seed.js
Expected — save this line 
API key (shown once):  psk_a1b2c3d4e5f6_<secret>

It is shown once and cannot be retrieved. Put it in your password manager now.

About that key

It carries org_owner permissions. Any key it issues can only ever carry a subset of its own permissions — so a key you hand out cannot escalate. Issue a separate, narrower key for anyone else rather than sharing this one.

Reach the console over an SSH tunnel — it is an operator surface, not a public one:

from your laptop
$ ssh -N -L 9200:127.0.0.1:9200 ubuntu@<vm-ip>
# then open http://127.0.0.1:9200/
08

Commission the charge point — four calls, in this order

A production gateway refuses unknown identities and demands credentials. Both have to exist before the charger dials in. The order matters: setting the security profile before the key exists is refused, and that refusal is the point.

from your laptop, through the tunnel
$ export K=psk_...            # the key from step 7
$ export API=http://127.0.0.1:9200
$ export ID=AUTEL-DC60-JKT-001 # exactly as Autel will configure it

# 1. register the identity — creates it in pending_adoption
$ curl -sS -X POST $API/v1/charge-points \
    -H "Authorization: Bearer $K" -H 'Content-Type: application/json' \
    -d "{\"ocppIdentity\":\"$ID\",\"siteId\":\"<site-uuid>\"}"

# 2. issue the AuthorizationKey — SHOWN ONCE
$ curl -sS -X POST $API/v1/charge-points/$ID/authorization-key \
    -H "Authorization: Bearer $K"

# 3. set the security profile (note: PUT, not POST)
$ curl -sS -X PUT $API/v1/charge-points/$ID/security-profile \
    -H "Authorization: Bearer $K" -H 'Content-Type: application/json' \
    -d '{"profile":2}'

# 4. activate — this is what lets it transact
$ curl -sS -X POST $API/v1/charge-points/$ID/activate \
    -H "Authorization: Bearer $K"
Expected 
1 → {"ok":true,"status":"pending_adoption","next":[...]}
2 → {"key":"df3e8bfe…","warning":"This key is shown once…"}
3 → {"ok":true,"profile":2}
4 → {"ok":true}

Get the siteId from GET /v1/charge-points, or create a site in the console first. Step 1's response lists the remaining steps back to you, so you do not have to keep this page open.

Set the key on the charger before raising the profile

Configure the AuthorizationKey on the unit first, then step 3. The other order leaves a unit that cannot connect and an installer standing next to it.

09

Prove it works before the real hardware arrives

The repository ships a virtual charge point. Point it at your live gateway and run a full session, so integration day is not the first time anything has connected.

on the VM, or anywhere with node 22
$ export PLUGSURE_KEY=psk_...
$ npx tsx tools/simulator/autel-sim.ts \
    --url wss://ocpp.plugsure.id/ocpp \
    --id $ID --auth-key <the AuthorizationKey> \
    --scenario happy
Expected 
--- happy: PASS ---

The scenario verifies against the API that the CSMS billed exactly the energy the simulator delivered. Without PLUGSURE_KEY those checks now fail rather than quietly skipping.

Worth running the harder ones too, since they cost nothing: --scenario offline-replay (store-and-forward after a WAN drop), --scenario reconnect-storm, --scenario meter-rollover.

When a charger will not connect

Every attempt is logged before the upgrade completes — source IP, path, offered subprotocols, TLS state, whether credentials were sent, and the outcome. That log is the single most useful thing on integration day.

read the attempt log
$ curl -sS "$API/v1/connection-attempts?limit=20" -H "Authorization: Bearer $K" | jq
StatusWhat it meansFix
101Connected—
400No supported subprotocol offeredSet the unit to OCPP 1.6J. We advertise ocpp1.6 only, deliberately.
401Missing or wrong Basic credentialsUsername must be the identity, byte-for-byte; password is the AuthorizationKey.
403Plaintext at security profile 2The unit is using ws://. It must use wss://. If every unit gets this, check OCPP_TRUST_PROXY_PROTO.
404Identity not registeredRun step 8.1. The identity is case-sensitive and character-exact.
PendingConnected and authenticated, but not activatedNot an error. Run step 8.4.
