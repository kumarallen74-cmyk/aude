# WhatsApp Business (Meta Cloud API)

PlugSure sends driver sign-in codes through **one WhatsApp Business Account
(WABA)** owned by the platform operator: the *Driver sign-in codes*
integration with the provider *WhatsApp (Meta Cloud API)*. From v1.10.0 its
health is on **Operate → WhatsApp**: the number's quality rating and messaging
limit, the templates PlugSure needs, and how many codes and alerts were
delivered, read or failed.

From v1.11.0, customers who write to that number land in a **support inbox**
(Operate → WhatsApp → Inbox), where an **AI assistant (Claude)** can answer
them or draft answers for staff: section 3.

This page is the setup, step by step: first at Meta, then in the PlugSure
console.

## 1. At Meta

You need admin access to the company's **Meta Business portfolio**
(business.facebook.com).

1. **Business portfolio.** Use the company's portfolio, or create one under
   *Business settings*. Business verification is not required to start, but it
   raises the messaging limit and is needed for a display name with the
   company's name.
2. **Meta app.** At developers.facebook.com → *My Apps* → *Create app*, choose
   the type *Business*, link it to the portfolio, and add the **WhatsApp**
   product. This creates (or connects) the **WhatsApp Business Account**.
3. **Phone number.** Under *WhatsApp → API Setup* → *Add phone number*, register
   the number that sends the codes. It must not be in use in the WhatsApp or
   WhatsApp Business **app**. Set the display name (Meta reviews it) and verify
   the number by SMS or voice. Note two IDs on that page:
   - **Phone number ID**: the sending number's ID, not the number itself.
   - **WhatsApp Business Account ID** (WABA ID).
4. **System User and permanent token.** Business settings → *Users → System
   users* → *Add* (role *Admin*). Then:
   - *Assign assets*: the app (full control) and the WhatsApp account (full
     control).
   - *Generate new token* for the app, expiry **Never**, with the permissions
     **`whatsapp_business_messaging`** and **`whatsapp_business_management`**.
   - Copy the token. Meta shows it only once.

   Do not use the temporary 24-hour token from API Setup: sign-in codes stop
   the next day.
5. **App secret.** App settings → *Basic* → *App secret* → *Show*. PlugSure uses
   it to check the signature (`X-Hub-Signature-256`) on every webhook call.
6. **Payment method.** Business settings → *WhatsApp accounts* → *Payment
   settings*: add a card. Authentication and Utility conversations are billed
   per message. Without a valid payment method, sending fails with code
   131042.
7. **Templates** (WhatsApp Manager → *Message templates* → *Create template*):
   - **`plugsure_otp`**: category **Authentication**, language **Indonesian
     (`id`)**, with a **copy-code** button. Meta writes the text itself
     ("*{{1}}* adalah kode verifikasi Anda…"). You can add the security notice
     and the expiry (5 minutes). PlugSure sends the code as the body parameter
     and again for the button.
   - **`plugsure_alert`** (only if operator alerts go out from this number):
     category **Utility**, language `id`, with the body parameters your alert
     channel sends (Alert routing → WhatsApp; see `src/services/alert-format.ts`
     for the order).

   Approval usually takes minutes. A template that is *rejected* or *paused*
   shows on the WhatsApp dashboard and raises a platform alert (once the
   webhook is set up).

The webhook is set in step 3 of the next section, after PlugSure has generated
the URL and the verify token.

## 2. In the PlugSure console

You need a platform administrator account. The WhatsApp settings live on the
sign-in codes integration that already sends the codes. There is no second
WhatsApp configuration.

1. **Govern → Integrations → Driver sign-in codes → Change**, provider
   **WhatsApp (Meta Cloud API)**:
   - *Phone number ID* and *Access token*: the System User token.
   - *Template name* `plugsure_otp`, *language* `id`; keep *copy-code button*
     ticked.
   - New in 1.10.0, optional, for the dashboard:
     - **WhatsApp Business Account ID**, for templates and account status.
     - **App secret**, which verifies Meta's delivery-status webhook.

     A configuration saved before 1.10.0 keeps working without them.
   - Leave the *Graph API version* and the base URL as they are.

   If the main channel is SMS and WhatsApp is the **fallback**
   (*Sign-in codes — fallback*), set these fields there instead. The dashboard
   uses the main channel's WhatsApp settings, else the fallback's.
2. Run **Test** with your own number. It checks the token, reads the sender's
   display number and name, and sends a real code.
3. **Webhook.** Saving shows a **callback URL**
   (`https://<OCPP host>/hooks/whatsapp-cloud/<key>`) and a **verify token**,
   both generated by PlugSure. They stay on the sign-in codes card and under
   *Operate → WhatsApp → Setup*. A configuration from before 1.10.0 gets them
   the next time it is saved. In the Meta app:
   1. Go to *WhatsApp → Configuration → Webhook → Edit*.
   2. Paste the URL and the token, then click *Verify and save*. Meta calls the
      URL and PlugSure echoes the challenge only for that token.
   3. Under *Webhook fields*, subscribe to `messages`,
      `message_template_status_update`, `phone_number_quality_update` and
      `account_update`.

   Without the app secret, PlugSure refuses Meta's calls (403): they cannot be
   verified. Set `PUBLIC_BASE_URL` on the API so the URL shown is the public
   one. `/hooks/*` must be reachable from the internet. `deploy/Caddyfile`
   routes it on the OCPP host, next to `/pay/*`.
4. **Operate → WhatsApp** (right under the Dashboard):
   - *Overview*: connection, quality rating (GREEN / YELLOW / RED), messaging
     limit, display name status, when the webhook last called, and 7 or 30 days
     of sent / delivered / read / failed. The numbers include operator alerts
     sent from the same number.
   - *Templates* (needs the WABA ID): every template on the WABA, PlugSure's
     marked, with a link to WhatsApp Manager.
   - *Messages*: every message, filterable by purpose and status.
   - *Setup*: the webhook values again, and a **test send** of any approved
     template.

**Operator alerts on the same Meta app.** A Meta app has one callback URL. If
an operator's alert channel (Govern → Alert routing → WhatsApp) sends from the
same app, its delivery statuses arrive at the sign-in codes webhook. They are
applied to the alert log there, and a failed alert still falls back to SMS.
The channel's own `/hooks/whatsapp/<key>` URL is only needed for an alert
channel on a different Meta app.

## 3. Customer support with Claude (v1.11.0)

Customers who write to the WhatsApp number (a driver replying to a sign-in
code, or anyone who has it from plugsure.com) arrive in **Operate → WhatsApp →
Inbox**, one conversation per number. Without anything more, staff answer them
there and an operator alert (*WhatsApp customer waiting for staff*) tells
whoever is on call. The webhook needs the **`messages`** field subscribed
(section 2, step 3).

To have **Claude** answer them:

1. **Anthropic account.** At platform.claude.com, under PT. Railsure
   Solutions Indonesia's organisation: *Settings → Billing* (a payment method
   or credits), then *Settings → API keys → Create key*. Copy the key
   (`sk-ant-api…`); it is shown once. A spend limit on the workspace caps the
   bill (*Settings → Limits*).
2. **Govern → Integrations → WhatsApp AI support** → *Connect*, provider
   *Claude (Anthropic API)*:
   - **Anthropic API key**: the key from step 1. Sealed like every secret.
   - **Replies**: start with **Drafts** (Claude writes, staff check and send),
     then **Automatic** once the drafts are right. **Off** keeps the inbox
     without AI.
   - **Model**: *Claude Opus 5.5* (default, the most capable), *Sonnet 5.5*
     (faster, half the price) or *Haiku 5.5* (fastest, cheapest).
   - **What Claude should know**: your support hours, how payment and refunds
     work, prices that are not on the chargers, links (plugsure.com/pricing,
     /refunds, /terms), what to do when a charger does not start. Claude answers
     from this and from PlugSure's live data, and says when it does not know.
   - Advanced: the assistant's name, the handover message, and the reply
     limits (per customer per hour, default 15; all customers per 24 hours,
     default 1,000).
   - **Test** sends one tiny request with the key and model.
3. Watch the **Inbox** for a few days in draft mode, improve the knowledge
   text, then switch to automatic.

**What Claude does.** It replies in the customer's language (Bahasa Indonesia
by default), briefly, in WhatsApp style. It looks things up with four read-only
tools:

| Tool | What it returns |
|---|---|
| `find_stations` | Public stations by name, street or area, or nearest to a location the customer shares: address, free chargers now, fastest charger, price per kWh. |
| `charger_status` | One charger's live status, by the code printed on it or the SPKLU id. |
| `my_recent_sessions` | The last five sessions and payments of the PlugSure account registered on **the number writing**, and nobody else's. |
| `hand_off_to_staff` | Passes the conversation to staff, with a one-line reason. |

It **cannot change anything**: no refunds, no starting or stopping a charge, no
account changes. It hands those to staff, as it does when the customer asks for
a person, when it cannot help, or when the reply limits are reached. The
customer then gets the handover message, the conversation shows **staff** in
the inbox, and an operator alert is raised. A staff reply resolves the alert.

**The inbox.** Filter by who answers (staff, AI, closed). Open a conversation
to see the messages with the delivery status of each reply, and:

- **Send** a reply. Staff take the conversation over and the assistant stops,
  except in draft mode, where sending its draft keeps it drafting.
- **Suggest reply** asks Claude for a draft, whoever has the conversation.
- **Hand to AI**, **Take over**, **Close**. A new message reopens a closed
  conversation with the assistant.

WhatsApp allows free-form replies only **within 24 hours** of the customer's
last message. After that the reply box is disabled until the customer writes
again.

**Cost.** Each AI reply is one to three requests to the Anthropic API: the
instructions and knowledge (cached after the first request), the last 24 hours
of the conversation, and the tool results. Token counts are on each AI reply in
the inbox and in total on the overview. Opus 5.5 costs US$4 per million input
tokens and US$20 per million output tokens; Sonnet 5.5 $2 / $10; Haiku 5.5
$0.10 / $0.50. Meta does not charge for replies within the 24-hour window.

**Refusals.** On Opus and Sonnet, if Anthropic's safety systems decline a
request, the request is re-run on Anthropic's recommended fallback model
(`fallbacks: "default"`). If that also declines, the conversation goes to
staff.

## Privacy

- **Masked numbers only.** The message ledger (`whatsapp_message`) stores the
  recipient as `+6281****890`, never the full number. **Sign-in codes are never
  stored**, and neither is the text of a message.
- **Retention.** Messages are kept **180 days**. Account events (template
  status, quality, account updates) are kept 90 days, at most the last 500.
  The hourly retention worker deletes older rows.
- **Support conversations (v1.11.0).** Customers' messages and the replies are
  stored as text (media is noted, not kept), **90 days**. The customer's number
  is stored sealed (`SECRETS_KEY`), because a reply needs it, and shown masked.
  With WhatsApp AI support on, the conversation's last 24 hours go to Anthropic
  to write each reply. Under its commercial terms, Anthropic does not train its
  models on API data by default. Mention it in the
  privacy policy (plugsure.com/privacy.html).
- **Platform administrators only.** The dashboard, the inbox and their API
  (`/v1/whatsapp/*`) need `platform:admin`. Test sends are audited
  (`whatsapp.test_sent`, number masked), and so are staff replies and handovers
  (`whatsapp.support_reply`, `whatsapp.support_handler`).

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| Meta: "The URL couldn't be validated" | The verify token does not match. Copy it again from *WhatsApp → Setup*; it is case-sensitive. The URL is not reachable: check `/hooks/*` in Caddy and that `PUBLIC_BASE_URL` is the public host. |
| Webhook calls answered **403** | No app secret is saved on the sign-in codes integration. Save it (Meta app → App settings → Basic). |
| Webhook calls answered **401** (API log: invalid signature) | The app secret saved is not this app's. Copy it again and save it; a reset app secret must be saved again too. |
| Webhook calls answered **404** | The URL's key belongs to a sign-in codes integration that was removed or switched to another provider. Paste the current URL. |
| *Templates* tab: "add the WhatsApp Business Account ID" | Save the WABA ID on the sign-in codes integration. |
| *Last call: nothing received* on the dashboard | No subscription for the `messages` field, or the app is in development mode with no webhook fields subscribed. |
| Code 190 | The token expired or was revoked. Generate a System User token that never expires. |
| Code 10 / 200 | The token lacks `whatsapp_business_messaging` or `whatsapp_business_management`, or the System User is not assigned to the WABA. |
| Code 132001 "template does not exist" | Wrong template name or language (`id` ≠ `id_ID`), or the template is not approved yet. The *Templates* tab shows what exists. |
| Code 132000 | The number of parameters does not match the template. An Authentication template takes the code once in the body and once for the button: keep *copy-code button* matching the template. |
| Template **PAUSED** / **DISABLED** | Recipients blocked or reported it. Meta pauses it for 3 to 6 hours, then disables it if it happens again. A platform alert (*WhatsApp template paused or rejected*) is raised, critical for the sign-in template. Edit the template, or keep an SMS fallback. |
| Quality rating **RED**, or the messaging limit lowered | Too many recipients block or report the number. A platform alert (*WhatsApp number quality low*) is raised. Send only what drivers asked for (codes) and keep templates clear. The rating recovers over about 7 days. |
| Code 131026 / failed "message undeliverable" | The number has no WhatsApp or an outdated app. The SMS fallback (if configured) sends the code instead. |
| Code 131030 | The number is Meta's test number, which only sends to up to 5 allowed recipients. Register the real number. |
| Code 131042 | Billing problem: add or fix the payment method on the WhatsApp account. |
| Inbox empty although customers write | The `messages` webhook field is not subscribed, or the webhook is answered 403 (no app secret). |
| Claude does not answer | *WhatsApp AI support* not connected, its *Replies* set to *Off* or *Drafts* (look for the draft in the conversation), or the conversation is with staff (*Hand to AI*). A note in the conversation gives an API error. |
| Note: "the Anthropic API key is invalid" | The key was revoked or mistyped. Create a new one and save it. |
| Note: "Anthropic's rate limit" | The organisation's rate limit at Anthropic. The next message is tried again. Raise the limit (platform.claude.com → Limits) or lower the reply limits. |
| A conversation went to staff: "more than N AI replies…" | The per-customer hourly limit was reached (an endless chat, or a loop with another bot). Answer it, or *Hand to AI*. |

Platform alerts go to the platform operator's organisations, the same way as
background-worker alerts: `OPS_ALERT_ORG_ID`, or else the organisations of the
platform administrators. Route them with a rule on the alert type *WhatsApp …*
(Govern → Alert routing).
